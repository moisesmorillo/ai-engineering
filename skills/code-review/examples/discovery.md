# Review Discovery Examples

These examples exercise the algorithm in [`../checklists/review-discovery.md`](../checklists/review-discovery.md). They illustrate evidence-based decisions, not repository-specific rules. In every non-ambiguous scenario, the user invokes only:

```text
/skill:code-review
```

| Scenario | Repository evidence | Expected discovery and review behavior |
|---|---|---|
| **A — Active feature PR** | The current branch has an open PR against the repository's default branch. Its complete diff adds a bounded Fetch-based outbound adapter. A current milestone defines this as the transport slice and defers automatic synchronization. An accepted ADR defines exact mutation-effect semantics. Existing code contains ETag, receipt, media-type, and acknowledgement primitives. CI/task configuration names the canonical validation command. | Review the full PR merge-base-to-head range automatically. Use the diff to discover the transport milestone and ADR; scrutinize HTTP boundaries, effect certainty, acknowledgement parsing, and failure classification. Search repository-wide for and prefer the existing protocol helpers. Treat deferred autosync as out of scope, not a defect. Run or inspect the canonical validation and state what it covered. Do not require the user to name the PR, slice, ADR, risks, or existing helpers. |
| **B — Local uncommitted bug fix** | No PR or meaningful branch diff exists. The working tree modifies two tracked files. Nearby source contracts and tests describe the bug's intended behavior. | Use `HEAD` as the baseline and the staged/unstaged working-tree diff as the target; include relevant untracked tests if present. Discover nearby contracts and repository-native validation. Disclose that remote CI does not cover the local overlay. Do not ask for a PR number. |
| **C — Stacked or multi-commit PR** | The active PR/branch contains several commits after its merge base; the last commit is only a corrective layer on earlier feature commits. Local `HEAD` may also be one unpublished commit ahead of the hosted PR head. | Review the complete PR-equivalent `merge-base(base, head)..head` range, not only `HEAD^..HEAD` or the latest commit. Compare local and hosted heads; when local `HEAD` is a verified descendant of the hosted PR head, include the unpublished commit as part of the local branch target and disclose that hosted CI has not covered it. Ask a concise question instead if the heads materially diverge. Inspect behavior composed across all included commits and files. |
| **D — Ambiguous repository state** | Available session and repository evidence identify multiple plausible repositories, targets, or bases whose diffs differ materially, with no reliable active choice. | Ask one concise question for the missing choice, such as “Should I review the open PR in repository A or the uncommitted changes in repository B?” Do not invent a range or issue findings before the target is resolved. |
| **E — Phased milestone** | The current milestone and accepted plan say this slice implements persistence only; network integration belongs to a later slice. The diff matches the persistence capability. | Record network integration as explicitly deferred. Review persistence contracts, storage safety, concurrency, migration, and recovery as applicable. Do not manufacture a “network integration missing” finding. |
| **F — Stale documentation conflict** | A historical planning document conflicts with an accepted current ADR, current source contract, and focused tests. Repository status/links show the planning document is superseded. | Record the conflict and use the corroborated current contract. Report documentation drift if it can mislead maintainers; do not silently blend both behaviors or let the stale plan override current evidence. Ask only if source status remains materially ambiguous. |
| **G — Corrective re-review** | In the same session and active PR, a previous MAJOR finding is available in conversation and a corrective commit changes the affected code and tests. | Rediscover the same PR and retain its valid original baseline. Verify the prior MAJOR individually, inspect the corrective delta and the complete current change for regressions, rerun relevant canonical validation, and rebuild the Review Brief if scope or risk changed. Do not ask the user to paste the prior finding or original review prompt again. |
| **H — Protocol-heavy adapter with structural concentration** | A changed 1000+ line Fetch adapter exports dependency interfaces and one implementation, constructs requests, reads secrets, admits work, owns `AbortController` lifecycle and bounded streaming, maps DTOs, classifies statuses and mutation-effect certainty, and introduces HTTP/header/status literals. | Select it as a structural candidate without the user asking about file length or magic values. Inventory responsibilities; explicitly assess cohesion, public-contract placement, status/effect decision-table ownership, protocol-literal ownership, and lifecycle/public-contract documentation. Trace the status/failure/effect/retry call chain, search repository-wide for contract and protocol owners, and visibly report the assessment. Treat size as a signal only; report only evidenced cohesion or drift risks. |
| **I — Repository-wide structural shortlist** | A baseline review finds a large generated parser, a generic manager with many unrelated methods, a protocol-heavy adapter, and several ordinary small modules. | Use relative size, exports/methods, concern-spanning imports, helper clusters, and protocol literals to select a small risk-ranked shortlist. Inventory each candidate before deciding: the parser may be cohesive and produce no finding; the manager or adapter may warrant NOTE/MINOR/MAJOR only if the inventory establishes mixed ownership or drift risk. Do not turn raw metrics into a repository-wide finding list. |

The examples intentionally keep the domain generic. An adapter or persistence change may require different scrutiny in another repository when its diff, contracts, ADRs, or architecture provide different evidence.
